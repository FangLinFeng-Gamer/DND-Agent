# 游戏开局与房间后端设计

## 一、目标

本设计用于支持新的游戏主流程：

1. 玩家在 `/game` 选择剧本和一支角色队伍。
2. 后端创建一局冒险，并锁定该冒险的剧本和队伍。
3. 玩家进入 `/game/{adventureId}` 后，DM Agent、战斗、地图和消息都围绕这支固定队伍运行。

当前代码中的冒险仍以单个 `character_id` 为核心。本设计将冒险升级为队伍模型，同时保留旧字段的兼容策略。

## 二、核心约束

1. 一局冒险必须绑定 1 到 6 名玩家角色。
2. 玩家角色数量限制只约束 `characters` 表中的玩家角色，不约束 NPC、敌人、召唤物和地图 token。
3. 冒险创建后，`story_id` 和队伍成员不可修改。
4. 已创建冒险继续使用创建时的 `story_snapshot_json`，后续修改剧本不影响旧冒险。
5. DM Agent 读取完整队伍上下文，而不是只读取单个角色。
6. 战斗开始时，所有本局队伍成员都进入玩家阵营参与者列表。
7. 地图 token 同步使用完整战斗参与者列表，包含所有玩家角色和敌方参与者。

## 三、现有状态存储能力

后端已经具备基础状态存储能力，当前主要落在 SQLite 中：

1. `adventures`
   - 保存一局冒险的标题、世界、剧本、兼容用 `character_id`、状态、摘要、当前场景 JSON 和剧本快照。
   - `current_scene_json` 是当前场景状态的主要存储位置。
2. `messages`
   - 保存冒险消息历史，包括玩家消息、DM 消息和相关 metadata。
   - DM Agent 流式回复结束后仍会落库为普通消息。
3. `combat_states`
   - 保存每局冒险当前战斗状态。
   - 包含是否激活、轮数、当前回合索引和参与者 JSON。
4. `map_scenes`
   - 保存冒险地图场景、网格、比例尺、背景色、active 状态和场景 metadata。
5. `map_scene_items`
   - 保存地图底图、道具、图层上的资源摆放信息。
6. `map_combat_tokens`
   - 保存战斗参与者在地图上的 token 坐标、尺寸、速度、触及范围、可见性和 metadata。
7. `map_walls`、`map_lights`、`map_fog_shapes`
   - 保存墙体、光源和迷雾等地图扩展状态。
8. `world_events`
   - 保存 DM Agent 或后端流程产生的重要世界事件，用于长期记忆和上下文摘要。
9. `character_creation_sessions`、`character_creation_messages`
   - 保存角色创建草稿、会话状态、修订号和角色创建对话历史。
10. `llm_models`
   - 保存模型配置和当前激活模型状态。

因此本次“游戏房间”设计不是从零开始增加状态存储，而是在现有状态存储基础上补齐多人队伍绑定、队伍读取和多人战斗上下文。

## 四、数据模型设计

### 现状

当前 `adventures` 表包含：

```text
id
title
world_id
story_id
character_id
status
summary
current_scene_json
story_snapshot_json
```

其中 `character_id` 只能表达单角色冒险。

### 目标模型

新增冒险队伍成员表：

```sql
CREATE TABLE IF NOT EXISTS adventure_characters (
    adventure_id INTEGER NOT NULL,
    character_id INTEGER NOT NULL,
    party_order INTEGER NOT NULL,
    role TEXT NOT NULL DEFAULT 'player',
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (adventure_id, character_id)
);

CREATE INDEX IF NOT EXISTS idx_adventure_characters_adventure
ON adventure_characters(adventure_id);

CREATE INDEX IF NOT EXISTS idx_adventure_characters_character
ON adventure_characters(character_id);
```

字段说明：

1. `adventure_id`：冒险 ID。
2. `character_id`：玩家角色 ID。
3. `party_order`：队伍显示顺序和默认 token 排布顺序。
4. `role`：一期固定为 `player`，为后续追随者、临时同伴或旁观角色预留。

### 兼容策略

短期保留 `adventures.character_id`：

1. 对旧冒险，读取时如果没有 `adventure_characters` 记录，则使用 `character_id` 补成单人队伍。
2. 新冒险创建时，`character_id` 写入队伍第一个角色，用于旧代码和旧测试兼容。
3. 新接口输出 `party_character_ids` 和 `party_characters`，前端优先使用新字段。
4. 后续稳定后，再考虑迁移并废弃 `character_id`。

## 五、Schema 设计

### `AdventureCreate`

目标请求体：

```json
{
  "title": "守望塔之路：第一夜",
  "story_id": "mistbell_tower",
  "party_character_ids": [1, 2, 3],
  "world_id": "default",
  "locale": "zh-CN"
}
```

兼容旧请求：

```json
{
  "title": "Watchtower Road",
  "story_id": "mistbell_tower",
  "character_id": 1,
  "world_id": "default",
  "locale": "en"
}
```

校验规则：

1. `party_character_ids` 优先。
2. 如果没有 `party_character_ids`，但存在 `character_id`，则转为 `[character_id]`。
3. 队伍数量必须在 1 到 6 之间。
4. 禁止重复角色 ID。
5. 每个角色 ID 必须存在。
6. `story_id` 必须存在。

### `AdventureOut`

目标响应：

```json
{
  "id": 1024,
  "title": "守望塔之路：第一夜",
  "world_id": "default",
  "story_id": "mistbell_tower",
  "character_id": 1,
  "party_character_ids": [1, 2, 3],
  "party_characters": [
    {
      "id": 1,
      "name": "塔夫",
      "race": "人类",
      "class_name": "德鲁伊",
      "level": 1,
      "hp_current": 8,
      "hp_max": 11,
      "armor_class": 14
    }
  ],
  "status": "active",
  "summary": "",
  "current_scene": {},
  "messages": []
}
```

`character_id` 标记为兼容字段，前端新逻辑不得依赖它判断本局队伍。

## 六、API 设计

### 创建冒险

`POST /api/adventures`

请求：

```json
{
  "title": "守望塔之路：第一夜",
  "story_id": "mistbell_tower",
  "party_character_ids": [1, 2, 3],
  "locale": "zh-CN"
}
```

行为：

1. 校验队伍人数和角色存在性。
2. 校验剧本存在性。
3. 生成开场 `SceneState`。
4. 写入 `adventures`。
5. 写入 `adventure_characters`。
6. 生成 DM 开场消息。
7. 返回完整 `AdventureOut`。

### 查询冒险

`GET /api/adventures/{adventure_id}`

返回冒险、消息、场景和队伍信息。队伍信息由 `adventure_characters` 和 `characters` 聚合得到。

### 查询冒险列表

`GET /api/adventures`

返回每个冒险的基础信息和队伍摘要。前端列表需要展示：

```text
冒险标题
绑定剧本
队伍人数
队伍角色名摘要
状态
```

### 禁止修改队伍

本阶段不提供以下接口：

```text
PATCH /api/adventures/{id}/party
PATCH /api/adventures/{id}/story
```

如果未来需要中途加入角色，应作为单独版本需求，并处理战斗、地图 token、DM 上下文和历史消息一致性。

## 七、服务层设计

### `AdventureService`

需要新增能力：

1. `create(adventure, scene, story)` 支持 `party_character_ids`。
2. `list()` 返回队伍摘要。
3. `get()` 返回完整队伍。
4. `get_party(adventure_id)` 返回 `list[CharacterOut]`。
5. `validate_party(character_ids)` 校验 1 到 6 人、去重、存在性。
6. `delete()` 删除 `messages`、`combat_states`、`adventure_characters`、地图关联数据后删除冒险。

### `DMService.create_adventure`

当前逻辑读取单个 `request.character_id`。目标改为：

1. 读取完整队伍角色。
2. 构造队伍摘要给开场生成逻辑。
3. 开场叙事应以“队伍”进入场景，而不是单个角色。
4. 没有模型时，模板 fallback 也要包含队伍成员名。

### `DMService.advance`

DM 推进时上下文需要包含：

1. 冒险基础信息。
2. 剧本快照。
3. 当前场景。
4. 消息历史。
5. 完整队伍角色卡摘要。
6. 当前战斗状态。
7. 当前 active map scene 和 token 环境。

在非战斗场景中，用户自然语言可能没有明确指定哪名角色行动。DM Agent 可以根据文本推断；如果无法判断，应追问玩家，不直接写入强规则状态。

### `MessageCreate`

可新增可选字段：

```text
actor_character_id: int | null
```

用途：

1. 前端在房间中选择当前发言或行动角色时传递。
2. 战斗中默认使用当前 combatant 对应角色。
3. 不传时由 DM Agent 根据内容和上下文判断。

该字段不用于绕过战斗回合规则；确定性战斗动作仍以 combat action API 为准。

## 八、战斗设计

### 开始战斗

当前 `start_combat` 只把 `adventure.character_id` 转成玩家参与者。目标改为：

1. 调用 `AdventureService.get_party(adventure_id)`。
2. 将所有队伍角色转换为 player combat participants。
3. 拼接请求中的敌人。
4. 调用 `CombatService.start_combat(participants)`。
5. 保存战斗状态。
6. 调用 `MapService.ensure_combat_tokens()` 同步所有参与者 token。

### 玩家动作

动作合法性：

1. 当前 combatant 必须属于 player side。
2. 当前 actor 必须在本局队伍中。
3. 当前 actor HP 必须大于 0。
4. 当前 actor 不能是 defeated。
5. 当前 actor 不能包含 incapacitated 等无法行动状态。
6. 攻击动作需要目标。
7. 如果存在 active map scene，则调用地图距离校验。

### NPC 动作

NPC 行动仍由 DM Agent 或 fallback 规则处理。上下文需新增：

1. 完整玩家队伍。
2. 每名角色当前 HP、AC、位置和可见状态。
3. 当前地图环境。
4. 周围敌我 token 距离。

未配置模型时，fallback NPC 行动规则继续执行：

1. 优先攻击最近且未倒地的玩家角色。
2. 如果自身低血量，优先撤退、回避或寻找掩体。
3. 如果无法攻击，向最近目标移动。
4. 如果没有合法目标，结束回合或执行防御动作。

## 九、地图与 token 设计

地图系统已有 `map_scenes` 和 `map_combat_tokens`。队伍模型下需要保证：

1. 战斗开始后，所有玩家队伍成员都有 player token。
2. token 初始位置按 `party_order` 排布，避免重叠。
3. `participant_name` 可能重复，后续应优先在 metadata 中写入 `character_id` 或 `participant_id`。
4. 地图攻击合法性使用参与者身份和 token 坐标，不依赖单个 `adventure.character_id`。

建议 `map_combat_tokens.metadata_json` 增加：

```json
{
  "character_id": 1,
  "combatant_id": "player:1"
}
```

## 十、DM Agent 上下文设计

DM Agent 的上下文包新增 `party`：

```json
{
  "party": [
    {
      "id": 1,
      "name": "塔夫",
      "race": "人类",
      "class_name": "德鲁伊",
      "level": 1,
      "hp_current": 8,
      "hp_max": 11,
      "armor_class": 14,
      "notable_proficiencies": ["感知", "自然"],
      "spells": ["治疗术"]
    }
  ],
  "current_actor": {
    "id": 1,
    "name": "塔夫"
  }
}
```

上下文原则：

1. 队伍角色卡摘要必须足够 DM 判断行动，但不能无限展开完整角色卡。
2. 当前 actor 在战斗中由 combat state 决定。
3. 非战斗中如果用户指定角色名，则将该角色作为 actor。
4. 如果用户说“我们一起调查”，DM Agent 可以按队伍行动处理，但强规则检定应明确由哪名角色主导。

## 十一、错误码设计

新增或复用错误码：

```text
party_required
party_too_large
party_duplicate_character
party_character_not_found
story_not_found
adventure_party_locked
actor_not_in_party
invalid_turn
combat_actor_cannot_act
attack_out_of_range
```

错误消息需要支持中文和英文。API 可以返回稳定错误码，前端用 i18n 显示本地化文本。

## 十二、迁移策略

1. 新增 `adventure_characters` 表。
2. 初始化 schema 时，对已有 adventure 行执行补偿迁移：

```sql
INSERT OR IGNORE INTO adventure_characters (adventure_id, character_id, party_order, role)
SELECT id, character_id, 0, 'player'
FROM adventures;
```

3. 所有读取冒险的路径优先读取 `adventure_characters`。
4. 如果补偿迁移失败或旧数据库缺少记录，读取时 fallback 到 `adventures.character_id`。

## 十三、测试要求

### 后端测试

1. `POST /api/adventures` 接收 `party_character_ids` 创建多人冒险。
2. 队伍为空时返回 `party_required`。
3. 队伍超过 6 人时返回 `party_too_large`。
4. 队伍存在重复角色时返回 `party_duplicate_character`。
5. 旧版 `character_id` 请求仍可创建单人冒险。
6. `GET /api/adventures/{id}` 返回 `party_character_ids` 和 `party_characters`。
7. 冒险创建后没有修改队伍和剧本的 API。
8. 战斗开始后，玩家阵营包含所有队伍角色。
9. HP 为 0 或 defeated 的角色无法执行动作。
10. 地图 token 同步包含所有玩家角色。
11. DM Agent 上下文包含完整队伍摘要。
12. 旧数据库迁移后，已有单人冒险可正常读取。

### 前后端集成测试

1. 前端创建 3 人队伍冒险，请求体包含 `party_character_ids`。
2. 创建成功后跳转 `/game/{id}`。
3. 刷新 `/game/{id}` 后仍能加载绑定队伍。
4. 房间中不会出现修改队伍入口。
5. 开始战斗后，回合顺序中包含所有队伍角色和敌人。

## 十四、实施顺序建议

1. 后端 schema 和 `AdventureCreate`/`AdventureOut` 支持队伍字段。
2. `AdventureService` 支持队伍创建、读取、列表和迁移。
3. `DMService` 创建冒险和推进上下文改为读取队伍。
4. 战斗开始改为加入所有队伍角色。
5. 地图 token 同步校验多人角色。
6. 前端 `/game` 开局准备页改为队伍多选。
7. 前端 `/game/{id}` 房间页改为绑定队伍和当前行动角色。
8. 补齐 i18n 和测试。
