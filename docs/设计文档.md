# DND-Agent 完整服务设计文档

## 一、引言

本文档描述当前版本 DND-Agent 的完整服务设计，范围包括后端服务、Agent Harness、角色创建流程、DM 游戏流程、前端页面、数据存储、接口边界和后续开发路线。文档依据当前 `main` 分支最新代码整理，代码基线为 `015d544`。

第一版目标是离线优先的 DND 5e 辅助游戏系统：用户可以创建角色、查看规则与世界信息、选择或创建剧本、基于同一剧本开启多局冒险，并通过 DM Agent 推进游戏。系统支持接入 OpenAI-compatible 大模型；没有可用大模型时，仍可使用离线模板和确定性规则流程完成基础游戏体验。

规则资料来源包括 `docs/5eDnD_玩家手册PHB_中译v1.72版.pdf` 和后端结构化规则资源。当前运行时不直接检索 PDF，而是使用 `backend/src/resources/phb2014` 中的结构化 JSON 规则数据，PDF 作为规则补全和人工校对的参考资料。

当前设计原则：

1. 后端以 FastAPI + SQLite 提供单体服务，首次启动自动创建数据库结构。
2. 前端使用静态 HTML/CSS/原生 ES module，由 FastAPI 直接挂载，不需要单独构建。
3. Agent 代码统一放在 `backend/src/agent`，服务层只负责 API 编排、持久化和业务调用。
4. DM Agent 采用 LangGraph + ReAct 主 Agent + 多子 Agent 架构；确定性流程使用 StateGraph。
5. 角色创建 Agent 外层采用 ReAct，状态变更必须经过确定性 StateGraph 校验。
6. 所有用户可见前端文案必须支持英文和中文切换，并将语言传递给后端 Agent prompt。

## 二、系统设计

### 2.1 Agent服务

Agent 服务负责理解用户意图、规划任务、调用工具和生成自然语言回复。当前实现分为 DM Agent、角色创建 Agent、LLM 接入、上下文管理、工具管理和提示词管理。

当前不引入 deerflow 或 hermes。原因是第一版系统更依赖明确的 DND 游戏状态、数据库事务、固定规则校验和前端交互状态，而不是通用流程编排框架。现有代码使用 LangGraph/LangChain 作为基础能力，自建轻量 Harness：

1. `backend/src/agent/dm`：DM Agent、prompt、memory、tool、subagent、LangGraph 工作流。
2. `backend/src/agent/character_creation`：角色创建 ReAct 外层、StateGraph、PHB 规则仓库、slot 提取、工具和派生角色卡计算。
3. `backend/src/agent/llm`：OpenAI-compatible 客户端和 LangChain ChatModel 适配。
4. `backend/src/agent/locale.py`：语言规范化和 prompt 语言要求。

后续如果需要更复杂的跨任务调度，可以继续基于 LangGraph 扩展；只有当现有 Harness 无法满足可观测性、分布式执行、任务重试或多人协作编排时，再评估外部 Agent 框架。

### 2.2 后端服务与 MCP-compatible 边界

原始设计中的 MCP 服务目前实现为后端内部服务和工具边界，还没有暴露真实 MCP 协议服务器。现有模块已经按 MCP 能力方向拆分：

1. 角色服务：创建、删除、修改、查询角色。
2. 世界与规则服务：查询种族、职业、背景、装备、法术、状态、战斗和冒险指导等世界条目。
3. 剧本与冒险服务：创建、选择、删除剧本和冒险会话。
4. 图片服务：记录图片生成请求和 prompt，暂未接入真实图片生成 Provider。
5. 剧情生成服务：DM Agent 基于当前冒险状态、历史消息、世界事件和大模型输出生成后续剧情。

真实 MCP Server 是后续路线，不影响当前前后端闭环。

### 2.3 GUI 模块

前端位于 `frontend/static`，入口是 `index.html` 和 `app.js`，模块目录是 `frontend/static/js`。当前页面包括：

1. 首页：展示游玩教程、默认剧本入口和主要导航。
2. 种族查询页：展示 5e 核心种族介绍、规则摘要、特性和亚种。
3. 角色创建页：包含角色创建 Agent 对话、结构化向导、角色草稿和已创建角色列表。
4. 剧本创建页：创建、编辑、删除自定义剧本；默认剧本禁止修改和删除。
5. 游戏页：选择角色与剧本，创建冒险，和 DM 对话，查看任务、场景、战斗、骰子和规则查询。
6. 大模型配置页：新增、编辑、测试、激活和删除 OpenAI-compatible 模型配置。

前端使用 `frontend/static/js/i18n.js` 管理中英文文案。用户切换语言后，前端重新渲染页面，并在创建角色、创建冒险、DM 对话等请求中传递 `locale`。

### 2.4 数据存储

当前使用 SQLite，本地数据库默认位于应用配置的数据目录下。`SQLiteStore.connect()` 会创建父目录，`init_schema()` 会在启动和 `/api/*` 请求进入时确保表结构存在，因此数据库不存在时首次启动会自动创建。

主要表：

1. `characters`：最终角色卡。
2. `world_entries`：世界、规则、种族、职业、战斗和冒险查询条目。
3. `stories`：可复用剧本模板。
4. `adventures`：某一次实际游戏会话。
5. `messages`：冒险会话消息历史。
6. `combat_states`：当前战斗状态。
7. `generated_assets`：图片生成请求记录。
8. `llm_models`：大模型配置，包含本地保存的 API key。
9. `world_events`：对世界产生重要影响的事件。
10. `character_creation_sessions`：角色创建会话和草稿。
11. `character_creation_messages`：角色创建 Agent 对话历史。
12. `character_creation_commits`：角色创建提交幂等记录。

数据库文件、`.env` 和日志文件必须保持在 `.gitignore` 中，不允许提交到远程仓库。API key 只能存在本地数据库或环境变量中，不能写入代码和文档示例。

### 2.5 大模型接入

模型配置通过 `/api/models` 管理，字段包括显示名称、provider、base_url、api_key、model_name、temperature、max_context_tokens 和 active 状态。

当前支持 OpenAI-compatible Chat Completions：

1. `base_url` 可以填写 API 根地址，例如 `https://api.deepseek.com`。
2. 也可以填写完整 `.../chat/completions` 地址。
3. 后端会在 `OpenAICompatibleClient._chat_completions_url()` 中统一归一化。
4. 连接测试接口会发送短消息并检查模型是否返回内容。

DM Agent 的结构化裁决默认使用 JSON mode；角色创建 ReAct 外层使用普通对话和工具调用，状态变更由工具返回的 StateGraphResult 作为权威结果。

## 三、详细设计

### 3.1 服务启动

入口文件是 `backend/src/main.py`。启动流程：

1. 创建 FastAPI 应用。
2. 读取应用配置并初始化 `SQLiteStore`。
3. 调用 `initialize_store()` 创建数据库表。
4. 执行 `WorldService.seed_defaults()` 写入默认世界条目。
5. 执行 `StoryService.seed_defaults()` 写入默认剧本 `mistbell_tower`。
6. 注册 API Router。
7. 将 `frontend/static` 挂载为静态站点。

中间件会在 `/api/*` 请求前再次确保 schema 存在，避免新环境或缺失数据库导致接口失败。

### 3.2 DM Agent

DM Agent 代码位于 `backend/src/agent/dm`，服务入口由 `backend/src/services/dm.py` 兼容导出，实际实现集中在 `backend/src/agent/dm/service.py`。

核心职责：

1. 根据剧本、角色和当前场景生成冒险开场。
2. 描述世界、环境、NPC、重要物品和当前目标。
3. 判断玩家动作是否需要属性检定、豁免或战斗处理。
4. 使用 NPC 属性、性格和当前剧情判断 NPC 行为。
5. 更新当前场景、任务目标、重要物品和世界事件。
6. 当模型不可用时，使用 `TemplateDMProvider` 提供离线模板回复。
7. 通过流式接口向前端输出 DM 回复，避免长时间空白等待。

DM Agent 当前架构：

1. `DMService`：冒险创建、同步推进、流式推进、模型选择和持久化编排。
2. `DMGraphRunner`：LangGraph 工作流，包含 `plan` 和 `resolve` 节点。
3. `DMSupervisor`：ReAct 主 Agent，只做规划和聚合，不直接修改状态。
4. `ReactSubAgentRegistry`：开放式 ReAct 子 Agent，包括探索、社交、剧情、NPC 和规则研究。
5. `DeterministicWorkflows`：固定流程 StateGraph，包括属性检定、豁免、战斗、场景更新、记忆和提交。
6. `NarrationAgent`：根据已裁决事实统一生成最终叙事文本。
7. `AgentMemoryManager`：构建上下文摘要，管理消息历史和世界事件。
8. `DMAgentTools`：读取角色、世界、冒险、消息和战斗信息。

DM 回复流程：

1. 前端发送玩家动作和 `locale`。
2. `AdventureLockService` 对同一冒险加锁，禁止并发 DM 回复。
3. 后端先持久化玩家消息。
4. 如果存在激活模型，`DMGraphRunner` 调用主 Agent 规划，再由确定性流程和模型裁决生成结果。
5. 如果无模型或模型失败，使用离线模板 fallback。
6. 重要世界变化写入 `world_events`。
7. 场景变化通过 commit workflow 写入 `adventures.current_scene_json`。
8. DM 消息写入 `messages`。
9. 流式接口持续发送 status、delta、final 等 NDJSON 事件。

DM 输出必须遵守 DND 基础循环：

1. DM 描述环境、位置、可见对象、NPC 和可行动选项。
2. 玩家说明角色要做什么。
3. DM 判断是否需要掷骰、属性检定、豁免、战斗或直接叙事。
4. DM 描述行动结果，并给出新的选择点。

### 3.3 角色创建 Agent

角色创建相关代码位于 `backend/src/agent/character_creation` 和 `backend/src/services/character_drafts.py`。

当前设计是“外层 ReAct + 内层确定性 StateGraph”：

1. `CharacterCreationReActAgent` 是最外层 Agent，负责理解自然语言、调用工具、回答规则问题和聚合结果。
2. `CharacterCreationToolRegistry` 暴露工具：读取草稿、搜索规则、解释选项、应用变更、校验草稿、确认创建。
3. `CharacterCreationStateGraph` 是权威状态变更入口，所有草稿修改、校验和提交都必须通过它。
4. ReAct Agent 必须读取工具返回的 StateGraphResult，并以其中的 `draft`、`next_step`、`validation_errors`、`committed` 作为权威状态。
5. 如果模型没有调用工具、模型失败或输出不可信，则回退到确定性 slot 提取和模板回复。
6. `CharacterCreationGuideService` 提供前端结构化向导数据，保证用户也可以通过页面控件完成创建。

当前前端向导暴露步骤：

1. `identity`：角色名称。
2. `class`：职业。
3. `race`：种族或亚种。
4. `background`：背景。
5. `abilities`：六项属性，使用 27 点购点制，基础属性范围 8 到 15。
6. `spells`：只有职业或种族规则需要时才出现。
7. `review`：确认创建。

状态模型 `CharacterDraft` 已预留更完整的 PHB 创建字段，包括熟练项、职业特性、可选规则、装备和冒险关联。当前 UI 向导尚未完全展开这些步骤，因此后续阶段应优先补齐装备、熟练项、职业选项和背景特性选择。

角色创建需要满足：

1. 用户中途修改名称、职业、种族、背景或属性时，依赖步骤必须被重新校验。
2. 职业变化会清空不再有效的法术、装备和职业选项。
3. 种族变化会重新计算属性加值和相关选择。
4. 确认创建必须是用户明确确认，不能由普通帮助问题触发。
5. `character_creation_commits` 使用 commit_key 保证重复确认不会创建重复角色。

### 3.4 PHB 规则资源

运行时结构化资源位于 `backend/src/resources/phb2014`：

1. `abilities.json`：6 项属性。
2. `backgrounds.json`：14 条背景记录。
3. `classes.json`：30 条职业与职业相关规则记录。
4. `equipment.json`：装备数据。
5. `feats.json`：53 条专长记录。
6. `proficiencies.json`：79 条熟练项记录。
7. `races.json`：29 条种族、亚种或血统相关记录。
8. `spells.json`：法术与职业法术列表。
9. `starting_equipment.json`：起始装备包。
10. `manifest.json`：资源版本与文件清单。

`PHBRuleRepository` 负责加载和搜索这些资源。角色创建的规则校验、法术选择、熟练项、派生角色卡和属性计算都应以该仓库为准。

### 3.5 角色模块

角色 API 位于 `backend/src/api/characters.py`，服务位于 `backend/src/services/characters.py`。

能力：

1. `GET /api/characters`：查询角色列表。
2. `POST /api/characters`：创建角色。
3. `GET /api/characters/{id}`：查询单个角色。
4. `PATCH /api/characters/{id}`：修改角色。
5. `DELETE /api/characters/{id}`：删除角色。

角色字段包括名称、种族、职业、等级、背景、阵营、生命值、护甲等级、六项属性、技能、熟练项、物品、法术和备注。角色创建 Agent 提交后也会写入同一张角色表。

### 3.6 世界与规则查询模块

世界 API 位于 `backend/src/api/world.py`，服务位于 `backend/src/services/world.py`。

能力：

1. 查询种族介绍、种族机制、标签、亚种和角色扮演说明。
2. 查询职业、背景、装备、法术、状态、战斗规则和冒险指导条目。
3. 支持按 `query` 和 `category` 搜索。

`world_entries` 是面向玩家查询的世界资料库，当前默认种子包含 9 个核心种族介绍和部分职业、背景、装备、法术、状态、战斗与设定条目。角色创建的严格规则不依赖 `world_entries`，而依赖 `phb2014` 结构化资源。

### 3.7 剧本与冒险模块

剧本是可复用的故事模板，冒险是一次实际游戏会话。同一个剧本可以开启多次冒险；不同冒险会因为玩家选择和世界事件产生不同状态。

剧本字段：

1. 标题。
2. 简介。
3. 世界背景。
4. 主线任务。
5. 开场地点。
6. 开场环境。
7. 开场目标。
8. 重要物品。
9. NPC 列表。

默认剧本为 `mistbell_tower`。默认剧本会在首次启动时自动写入，禁止删除和修改。用户自定义剧本可以创建、编辑和删除。

冒险字段：

1. 标题。
2. 关联剧本 ID。
3. 关联角色 ID。
4. 状态。
5. 摘要。
6. 当前场景。
7. 剧本快照。
8. 消息历史。
9. 世界事件。

冒险创建时会复制剧本快照，避免之后修改剧本影响已经开始的游戏。

### 3.8 战斗与骰子模块

战斗 API 集成在 `/api/adventures/{id}/combat/*`，服务位于 `backend/src/services/combat.py`。

当前支持：

1. 开始战斗，创建敌方参与者。
2. 记录先攻、回合、生命、护甲等级和参战者。
3. 提交战斗动作。
4. 结束战斗。

DM Agent 中的确定性 workflow 包含 `combat_agent`、`ability_check_agent` 和 `saving_throw_agent`。前端提供骰子托盘，便于玩家手动掷 d4、d6、d8、d10、d12、d20。

### 3.9 图片生成模块

图片 API 位于 `backend/src/api/assets.py`，服务位于 `backend/src/services/assets.py`。

当前实现是 prompt stub：

1. 接收图片生成请求。
2. 保存图片类型、对象 ID、prompt、状态和 metadata。
3. 返回生成记录。

暂未接入真实图片模型或文件存储。后续需要增加 Provider 抽象、异步任务、结果 URI、失败重试和前端展示。

### 3.10 前端交互设计

前端状态集中在 `frontend/static/js/state.js`。主要模块：

1. `api.js`：封装 HTTP 请求和 DM 流式响应读取。
2. `i18n.js`：中英文翻译、角色名/状态/世界消息本地化。
3. `ui.js`：通用渲染、错误显示、视图切换、输入中动画。
4. `game.js`：角色、冒险、DM 对话、战斗、规则查询。
5. `character-creation.js`：角色创建 Agent 对话、结构化向导、忙碌态和确认创建。
6. `stories.js`：剧本列表、创建、编辑、默认剧本展示。
7. `races.js`：种族列表和详情。
8. `models.js`：大模型配置。
9. `dice.js`：骰子托盘。

DM 和角色创建 Agent 等待回复时必须：

1. 展示 typing/loading 动画。
2. 禁用输入框和发送按钮。
3. 禁止用户在上一轮回复完成前再次发送。
4. 后端也要通过冒险锁避免同一冒险并发写入。

## 四、代码要求

1. 所有 Agent 相关代码必须放在 `backend/src/agent` 下，包括对话处理、记忆管理、prompt 管理、tool 管理、子 Agent 上下文管理和 Harness Engineering。
2. API Router 只做请求解析、错误映射和调用服务；不要把 Agent 逻辑写进 Router。
3. 服务层负责业务编排、数据库读写和事务边界；不要在前端直接拼接后端状态。
4. 角色创建状态变更必须经过 `CharacterCreationStateGraph`，不能让大模型直接生成最终角色入库。
5. DM 世界状态变更必须经过 commit workflow 或明确的服务方法，不能只写在自然语言回复里。
6. 前端新增任何文案都必须同步更新 `i18n.js` 的英文和中文键。
7. 后端 Agent prompt 必须带上用户当前语言要求。
8. 数据库、API key、日志、`.env` 和本地缓存不能提交到远程仓库。
9. 设计文档变更后应运行设计对齐测试和相关后端测试。
10. 保持不引入 deerflow 或 hermes，除非后续有明确需求证明当前 LangGraph + 自建 Harness 无法满足。

## 六、上下文和记忆设计

DM Agent 上下文来源：

1. 当前冒险和场景。
2. 角色卡。
3. 剧本快照。
4. 最近消息历史。
5. 世界事件。
6. 战斗状态。
7. 世界与规则搜索结果。

当上下文接近模型限制时，`AgentMemoryManager` 应摘要历史消息，并将重要事实写入 `world_events` 或冒险摘要。重要事件包括 NPC 死亡或背叛、关键物品被获得或毁坏、地点状态变化、阵营关系变化、任务目标完成或失败。

原则：

1. 短期对话用于当前叙事连续性。
2. `current_scene_json` 用于当前可操作环境。
3. `world_events` 用于长期世界变化。
4. `adventures.summary` 用于压缩后的剧情摘要。
5. 最终给玩家的文字由 narration agent 或模板统一输出。

## 七、当前限制

1. 还没有暴露真实 MCP 协议服务器，当前是 MCP-compatible 内部服务边界。
2. 图片生成只是记录 prompt，未接入图片 Provider。
3. PHB PDF 尚未作为运行时检索源；运行时依赖结构化 JSON 规则资源。
4. 角色创建状态模型已预留完整步骤，但前端向导当前只覆盖核心步骤和法术选择。
5. 世界查询库和 PHB 规则库是两套数据：前者面向玩家查询，后者面向规则校验，后续需要统一索引。
6. 前端是静态文件直出，没有构建产物 hash；浏览器可能缓存旧 JS，需要后续增加版本号或缓存控制。
7. 大模型 API key 当前保存在本地 SQLite 明文字段，适合本地开发；生产环境需要加密或改用密钥管理。
8. 部分历史兼容文件仍存在，例如未挂载的 legacy API 文件；后续可以清理。
